AI 코딩 도구가 빠르게 발전하고 있습니다. 이제 기능 개발을 요청하면 코드 작성은 물론 테스트까지 수행하고, 오류를 수정하거나 GitHub에 풀 리퀘스트(PR)를 생성하는 것도 가능합니다.

하지만 실제 개발 현장에서 AI 코딩 에이전트를 쓰다 보면 한 가지 문제가 생깁니다.

**AI가 코딩을 대신해 주는데, 그 AI를 관리하는 일은 여전히 사람 몫이라는 것입니다.**

에이전트 여러 개를 동시에 돌리면 개발자는 각 에이전트의 상태를 확인하고, 새 지시를 내리고, 결과를 검토해야 합니다. 에이전트가 많아질수록 관리 부담도 커집니다.

지난 10월 31일, 딥시크의 Harness 개발팀이 *Exploring Super-agent Design: Towards a More Autonomous Agent System*이라는 기술 문서를 발표하고 이를 구현한 `dsh-superagent-prototype`을 GitHub에 공개했습니다.

코딩을 더 잘하는 새 모델을 내놓은 것이 아닙니다. **AI가 여러 작업을 동시에 관리하고, 개발 환경에서 발생하는 이벤트를 확인하며, 필요한 작업을 스스로 수행하도록 만드는 시스템 구조**를 제안한 것입니다.

기존 [Claude Code나 Codex](/blog/rethinking-skills-prompts-gpt-6-astra)와 무엇이 다를까요? 공식 기술 문서와 GitHub 소스코드를 기준으로 살펴보겠습니다.

<br/>

## 1. 코딩 슈퍼 에이전트란 무엇인가

먼저 슈퍼 에이전트(Super-agent)는 새로운 LLM 모델의 이름이 아닙니다. 여러 AI 에이전트와 개발 도구를 연결해 지속적으로 작업을 수행하도록 설계한 **에이전트 운영 아키텍처**입니다.

기존 AI 코딩 도구의 사용 과정을 생각해 봅시다. 개발자가 오류 수정을 요청하면 에이전트가 코드를 분석하고 문제를 해결합니다. 이후 개발자가 결과를 확인하고 다음 작업을 지시합니다. 작업을 하나씩 진행할 때는 이 방식으로도 충분합니다.

하지만 개발팀에서는 동시에 여러 일이 벌어집니다.

- GitHub에 새로운 버그가 등록됩니다
- 개발자가 기능 개선을 요청합니다
- CI 테스트에서 오류가 발생합니다
- 코드 리뷰에 수정 요청이 추가됩니다
- 다른 개발자가 기존 작업의 요구사항을 변경합니다

이 모든 일을 사람이 확인해 개별 에이전트에 전달해야 한다면, 코딩 속도가 빨라져도 전체 생산성에는 한계가 있습니다.

딥시크는 에이전트가 특정 채팅창이나 실행 세션에 종속되지 않고 계속 동작하는 구조를 제안했습니다. 공식 문서는 슈퍼 에이전트의 특징을 네 가지로 정의합니다.

| 특징 | 의미 |
|---|---|
| **Continuous** | 여러 채널에서 발생한 대화를 하나의 연속된 작업으로 관리 |
| **Productive** | 여러 복잡한 작업을 병렬로 수행 |
| **Proactive** | 환경 변화를 감지하고 허용된 범위에서 선제적으로 행동 |
| **Persistent** | 장시간 실행하며 장애 발생 시 복구할 수 있는 구조 |

다만 이 네 가지는 딥시크가 제시한 **목표 특성**입니다. 현재 GitHub에 공개된 프로토타입이 이를 모두 완성했다는 뜻은 아닙니다.

<br/>

## 2. 핵심은 Router와 Worker의 역할 분리

이번 발표에서 가장 주목할 부분은 **Router–Worker 2계층 아키텍처**입니다.

![Router-Worker 아키텍처 핵심 구조](/images/blog/2026-11-03-deepseek-super-agent_architecture.webp)

여러 AI 에이전트를 동시에 실행한다고 해서 자동으로 협업이 이뤄지는 것은 아닙니다. 각자 따로 작업하면 전체 진행 상황을 파악하기 어렵고, 같은 코드에 중복 수정이 발생하거나 새 요청이 적절한 담당자에게 전달되지 않을 수 있습니다.

딥시크는 작업을 관리하는 Router와 실제 작업을 수행하는 Worker를 분리했습니다.

### Router — AI 개발팀의 조정 담당자

Router는 외부에서 발생하는 이벤트를 받아 어떤 작업을 수행할지 판단합니다. GitHub 이슈나 코드 리뷰 댓글, 개발팀 메시지 등을 확인하고 필요한 작업을 Worker에게 배정합니다.

중요한 특징은 **Router가 직접 코딩하지 않는다는 것**입니다. 개별 구현에 관여하기보다 작업을 분배하고, 상태를 파악하고, 개발자와 소통하는 데 집중합니다. 덕분에 특정 작업이 오래 걸려도 새 요청을 계속 받아 처리할 수 있습니다.

### Worker — 실제 코딩을 수행하는 에이전트

Worker는 Router로부터 작업을 배정받아 실제 개발을 수행합니다. 각 Worker에는 **독립적인 실행 세션과 작업 디렉터리**가 주어집니다.

한 Worker는 버그를 수정하고, 다른 Worker는 테스트를 작성하며, 또 다른 Worker는 새 기능을 구현하는 식입니다. 복잡한 작업에서는 Worker가 추가 하위 에이전트를 활용할 수도 있습니다.

### 전체 작업 흐름

![요청 발생부터 사람 검토까지의 6단계 작업 흐름](/images/blog/2026-11-03-deepseek-super-agent_workflow.webp)

| 단계 | 처리 주체 | 주요 역할 |
|---|---|---|
| 이벤트 수신 | GitHub / 메신저 | 새 요청이나 변경사항 발생 |
| 이벤트 평가 | Policy / Router | 처리 대상 여부 판단 |
| 작업 할당 | Router | 작업 생성 및 담당 Worker 결정 |
| 작업 실행 | Worker | 코드 분석·수정·테스트 |
| 결과 수집 | Router | 작업 완료 및 상태 확인 |
| 결과 전달 | GitHub / 메신저 | PR 생성, 결과 보고, 승인 요청 |

기존 코딩 에이전트가 **하나의 개발 작업을 해결하는 데 집중**했다면, 슈퍼 에이전트는 여러 작업이 발생하는 환경 전체를 지속적으로 관리하는 데 초점을 맞춥니다.

물론 Claude Code와 Codex에도 하위 에이전트와 병렬 실행 기능이 이미 있습니다. 딥시크가 멀티 에이전트를 처음 구현한 것은 아닙니다. 이번 발표의 차별점은 병렬 실행 자체보다 **상시 이벤트 수신과 전역 작업 조정, 독립 실행 세션을 결합한 운영 방식**에 있습니다.

## 3. 단순히 여러 에이전트를 실행하는 것과 뭐가 다른가

공식 기술 문서를 읽어보면 Router–Worker 구조보다 더 흥미로운 기술들이 나옵니다.

### ① 이벤트 기반 실행 — 명령하지 않아도 작업을 발견한다

일반적인 AI 코딩 도구는 사용자가 명령을 입력해야 작업을 시작합니다. 반면 슈퍼 에이전트는 GitHub 이슈나 CI 결과처럼 외부에서 발생하는 이벤트를 지속적으로 확인합니다.

여기서 모든 이벤트를 LLM에 전달하면 비용과 처리량 문제가 생깁니다. 딥시크는 두 단계 필터링 구조를 제안했습니다.

- **Fast Path**: 일반 프로그램 코드로 빠르게 판단할 수 있는 조건을 처리합니다. 허용된 사용자가 보낸 요청인지, 모니터링 대상 저장소의 이벤트인지 확인하는 식입니다.
- **Slow Path**: 규칙만으로 판단하기 어려운 요청을 LLM이 분석합니다. 개발팀 대화에서 버그가 언급됐을 때 단순한 의견인지, 실제 수정을 시작할 만한 요청인지 판단합니다.

이 구조는 처리 비용을 줄이고, 에이전트가 불필요한 대화에 무분별하게 개입하는 것을 막는 데 도움이 됩니다.

### ② Thread Subscription — 같은 작업의 후속 요청을 자동 연결

실제 개발에서는 하나의 작업이 여러 이벤트에 걸쳐 진행됩니다. GitHub 이슈에서 시작한 작업이 PR로 이어지고, 코드 리뷰에서 추가 수정 요청이 생기는 식입니다.

매번 Router가 전체 내용을 다시 분석해 담당 Worker를 찾으면 불필요한 비용이 발생합니다. Thread Subscription은 Worker가 특정 작업의 Thread를 구독해 후속 이벤트를 **직접** 받도록 합니다.

Worker A가 PR #42를 수정하고 있다면, 같은 PR에 새 리뷰 댓글이 달렸을 때 Worker A가 바로 이어받습니다.

### ③ Chain of Recall — 필요한 기억만 찾아 쓰는 방식

여러 작업을 오래 수행하는 AI에게는 컨텍스트 관리도 문제입니다. 모든 대화와 코드 변경, 작업 기록을 하나의 컨텍스트에 넣을 수는 없습니다.

딥시크는 Inline & Spill과 Chain of Recall을 제안했습니다. 자주 쓰는 정보는 현재 컨텍스트에 두고, 방대한 기록은 별도 저장소에 보관한 뒤 참조 정보로 필요할 때 가져오는 구조입니다.

모든 정보를 항상 기억하는 것이 아니라, **필요한 순간에 관련 기록을 찾아 활용하도록** 만드는 방식입니다.

### ④ Full-Duplex — 이전 작업이 끝나기 전에 새 요청을 처리

동기식 도구 실행에서는 긴 작업이 진행되는 동안 다음 요청을 처리하지 못할 수 있습니다. 딥시크는 오래 걸리는 명령을 백그라운드로 실행하고 완료 결과를 별도 이벤트로 전달하는 비동기 구조를 설명했습니다.

DeepSeek Harness에 이런 비동기 메커니즘이 이미 있지만, 발표 당시 기본 활성화 기능은 아니라고 밝혔습니다.

### ⑤ 장애 복구를 위한 Watchdog

장시간 동작하려면 프로세스가 살아 있는지 확인하는 것만으로는 부족합니다. AI가 무의미한 작업을 반복하거나 원래 목표에서 벗어나는 상황도 생기기 때문입니다.

딥시크는 별도 Watchdog 에이전트가 진행 상황과 장애 상태를 감시하는 구조, 그리고 클라우드의 Agent Loop·지속 상태 저장소·실제 명령 실행 환경을 분리하는 설계를 제안했습니다. 다만 이 부분은 **현재 프로토타입에 모두 구현된 기능으로 받아들이면 안 됩니다.**

## 4. 실제로 어떤 작업에 활용할 수 있나

### 사례 1. GitHub 버그 수정 자동화

사용자가 비밀번호 재설정 이메일을 받지 못하는 문제가 생겼다고 해봅시다. 개발자가 GitHub 이슈에 등록하고 에이전트에게 수정을 요청합니다.

슈퍼 에이전트는 요청을 검토해 작업을 생성하고 Worker를 배정합니다. Worker는 관련 코드를 확인하고 오류를 수정하며 테스트를 수행합니다. 작업이 끝나면 브랜치에 반영하고 PR을 생성합니다. 개발자는 결과와 테스트를 검토해 승인하면 됩니다.

이후 PR에 추가 수정 요청이 들어와도 연결된 Worker가 후속 작업을 이어갑니다.

### 사례 2. 여러 작업의 병렬 처리

| 요청 | 담당 Worker | 수행 작업 |
|---|---|---|
| 로그인 오류 수정 | Worker A | 원인 분석 및 버그 수정 |
| API 응답 개선 | Worker B | 성능 관련 코드 수정 |
| 테스트 코드 추가 | Worker C | 테스트 작성 및 검증 |

각 Worker는 독립된 환경에서 작업하고 결과는 Router를 통해 정리됩니다.

다만 같은 파일을 동시에 수정하면 충돌이 발생할 수 있어 브랜치 관리와 PR 검토가 필요합니다. **병렬 진행이 곧 안전한 자동 통합을 뜻하지는 않습니다.**

### 사례 3. 코드 리뷰 대응 자동화

AI가 만든 PR에 리뷰어가 "예외 처리 로직을 추가하고 실패 케이스 테스트를 보완해 주세요"라고 댓글을 남겼다고 해봅시다.

이 이벤트가 작업에 연결되어 있다면 해당 Worker가 수정 사항을 다시 분석하고 테스트를 보완합니다. 개발자가 같은 내용을 새 채팅창에 복사해 전달할 필요가 줄어듭니다.

### 사례 4. 개발팀 대화에서 문제를 발견해 조치

딥시크는 내부에서 운영 중인 슈퍼 에이전트가 팀 채팅 피드백을 분석해 문제를 재현하거나 수정한 사례를 소개했습니다.

중요한 점은 AI가 모든 대화를 마음대로 해석해 작업을 시작해서는 안 된다는 것입니다. 사전에 허용된 사용자, 이벤트 종류, 자동 작업 규칙을 정의해야 합니다.

실제로 공개된 프로토타입의 정책 모드는 소스코드에서 **`off` / `observe` / `auto` 세 가지로 정의되어 있고 기본값은 `observe`** 입니다. 이 모드에서는 선제적으로 발견한 작업 후보를 실행하지 않고 "받아들였을 것"이라는 기록만 남깁니다. 처음부터 전부 자동 실행하기보다, 어떤 요청을 처리할지 충분히 검증한 뒤 범위를 넓히는 쪽이 바람직합니다.

## 5. 처리 시간이 47% 줄었다? 실험 결과 뜯어보기

이번 발표에서 눈에 띄는 수치는 작업 완료 시간이 약 47% 감소했다는 결과입니다. 하지만 이것이 **AI의 코딩 능력이 47% 좋아졌다는 뜻은 아닙니다.**

딥시크는 여러 작업이 동시에 발생할 때 스케줄링과 작업 분배가 얼마나 효율적인지를 측정했습니다. 약 300개의 메시지와 20개의 작업 요청이 발생하는 상황을 구성했고, 각 방식을 5차례씩 실행했으며, 실제 코드 구현은 시간이 소요되는 도구 호출로 모의했습니다.

![실험 결과 - 처리 시간은 줄고 토큰 사용은 늘었다](/images/blog/2026-11-03-deepseek-super-agent_benchmark.webp)

| 아키텍처 | p50 완료 시간 | p95 완료 시간 | 캐시 읽기 토큰 |
|---|---:|---:|---:|
| Super-agent | 12.4분 | **15.7분** | 23.2M |
| Super-agent, Pass-through 제외 | 12.6분 | 15.5분 | 31.8M |
| 단일 세션 + Subagent, 일반 지시 | 20.4분 | 29.5분 | **6.1M** |
| 단일 세션 + Subagent, 위임 우선 | 13.8분 | 29.0분 | 10.8M |

p50은 작업의 절반이, p95는 작업의 95%가 해당 시간 안에 끝났다는 의미입니다. 슈퍼 에이전트의 p95는 15.7분으로, 일반적인 단일 세션 방식의 29.5분과 비교하면 약 47% 짧습니다.

그런데 다른 숫자도 봐야 합니다. 캐시 읽기 토큰이 23.2M으로, 단일 세션 방식의 6.1M보다 **약 3.8배 많습니다.** 작업 완료 시간을 줄이는 대신 더 많은 토큰을 쓴 것입니다.

Pass-through를 제거한 경우 완료 시간은 큰 차이가 없었지만 캐시 읽기 토큰은 23.2M에서 31.8M으로 늘었습니다. Thread의 후속 이벤트를 Worker에게 직접 전달하는 방식이 Router의 처리 부담을 줄이는 데 효과가 있다는 뜻입니다.

### 이 실험에서 확인할 수 없는 것

1. **실제 소프트웨어 개발 성능 측정이 아닙니다.** 모의 작업 기반의 스케줄링 실험입니다
2. **Claude Code나 Codex와 직접 비교한 실험이 아닙니다**
3. **반복 횟수가 각 방식당 5회로 제한적**이며 실제 개발 환경에서의 재현성은 추가 검증이 필요합니다

새로운 아키텍처의 가능성을 보여주는 초기 데이터로 이해하는 것이 적절합니다.

## 6. 공개된 오픈소스는 어디까지 구현됐나

이번 발표에서 가장 주의 깊게 봐야 할 부분입니다.

**GitHub:** [deepseek-ai/dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)

공식 README는 이것이 **"참고용 연구 프로토타입이며 딥시크의 공식 제품이 아니다"** 라고 명시합니다. 코드 상당 부분을 코딩 에이전트가 작성했고, 버그가 남아 있을 수 있으며 코딩 스타일도 일관되지 않을 수 있다고 밝힙니다.

더 중요한 문장도 있습니다. **"기술 문서에서 논의한 설계 중 일부는 향후 개발 방향이며 이 프로토타입에는 구현되어 있지 않다"** 는 것입니다. 공개 버전은 주로 **하나의 GitHub 저장소에서 발생하는 개발 작업을 처리하도록** 구현되어 있습니다.

### 설계 비전과 공개 버전 비교

| 기능 | 설계 문서 | 공개 프로토타입 |
|---|---|---|
| Router–Worker 분리 | 제안 | 구현 |
| GitHub 이벤트 수신 | 제안 | 구현 |
| 여러 Worker의 독립 작업 | 제안 | 구현 |
| 기존 Thread의 후속 이벤트 처리 | 제안 | 구현 |
| GitHub PR 기반 작업 결과 전달 | 제안 | 구현 |
| 사람의 개입이 필요한 작업 표시 | 제안 | 관리 패널 제공 |
| Feishu 메신저 연동 | 제안 | 선택적 지원 |
| 이메일·다양한 업무 채널 연동 | 확장 방향 | 기본 제공 범위 아님 |
| 클라우드·개인 PC 간 실행 환경 분리 | 제안 | 범용 기능으로 완성된 상태 아님 |
| 장기 실행 자율 복구 Watchdog | 제안 | 전체 설계와 동일한 구현 아님 |

공개된 시스템은 범용 AI 개발팀 관리 플랫폼이라기보다, **GitHub를 중심으로 동작하는 능동형 코딩 에이전트의 구현 사례**에 가깝습니다.

그럼에도 소스코드가 공개된 것은 의미가 있습니다. 에이전트가 어떻게 작업을 생성하고, 상태를 관리하고, 사람의 승인을 기다리는지 내부 구조를 직접 볼 수 있기 때문입니다. 라이선스는 **MIT**라 조건에 따라 수정과 상업적 활용이 가능합니다.

## 7. 직접 설치해서 써볼 수 있나

개발 환경을 구성할 수 있다면 테스트해 볼 수 있습니다. 다만 설치 후 바로 모든 기능을 쓰는 형태는 아닙니다.

먼저 슈퍼 에이전트가 동작할 기반인 **DeepSeek Harness**를 준비해야 합니다. Harness는 딥시크가 공개한 오픈소스 AI 에이전트 실행 플랫폼으로, 모델 연결·도구 실행·세션 관리를 플러그인으로 확장하는 구조입니다. 슈퍼 에이전트는 이 플랫폼 위에서 실행되는 별도 번들입니다.

### 1단계. DeepSeek Harness 실행

```
npx @deepseek-ai/dsh web
```

기본적으로 `http://127.0.0.1:3080`에서 웹 인터페이스가 열리고 브라우저가 자동으로 실행됩니다. 브라우저를 띄우지 않으려면 `--no-open`을 붙입니다. 이 단계는 슈퍼 에이전트가 아니라 Harness를 실행하는 단계입니다.

### 2단계. Super-agent 저장소 내려받기

```
git clone https://github.com/deepseek-ai/dsh-superagent-prototype.git
```

저장소에는 소스코드와 함께 설치 방법·아키텍처 문서가 들어 있습니다.

### 3단계. 개발 환경 준비

공식 `SETUP.md` 기준 필요한 것은 다음과 같습니다.

- **Node.js 22.19+ 또는 24+**
- **pnpm**
- **git 2.32+**
- **tmux**
- **Python 3.8+**
- **GitHub CLI 2.48+**

Harness에 사용할 AI 모델 제공자도 설정해야 합니다. 특정 딥시크 모델만 써야 하는 것은 아니고, Harness에 설정한 모델을 기반으로 동작하도록 설계되어 있습니다.

### 4단계. 코딩 에이전트로 설치 구성

설치 절차가 여러 단계라 공식 프로젝트는 **코딩 에이전트와 함께 설정하는 방식**을 권장합니다. 저장소를 연 코딩 에이전트에게 이렇게 지시하면 됩니다.

```
Read SETUP.md in this repository and set up dsh-superagent with me.
```

에이전트는 한 번에 하나씩 짧은 질문을 던지고, 전체 계획을 한 번 보여준 뒤 설치와 설정을 진행합니다. 저장소, 사용할 계정, 허용할 사용자, 작업 환경 등을 묻습니다.

### 5단계. GitHub에서 테스트

설치가 끝나면 허용된 GitHub 계정으로 이슈에 댓글을 남겨 작업을 요청할 수 있습니다.

```
@agent-account 로그인 오류의 원인을 분석하고 수정 PR을 만들어 주세요.
```

에이전트는 요청을 받아 작업을 생성하고 독립된 실행 환경에서 처리합니다. 관리 패널에서 작업 상태와 사람 확인이 필요한 항목을 볼 수 있습니다.

처음 테스트할 때는 실제 운영 서비스 대신 **별도의 테스트 저장소**를 쓰기를 권합니다.

## 8. Claude Code, Codex와 무엇이 다른가

딥시크의 슈퍼 에이전트를 Claude Code나 Codex의 상위 버전처럼 이해하는 것은 적절하지 않습니다. 모두 AI 기반 개발 자동화에 쓰이지만 초점이 다릅니다.

Claude Code와 Codex는 이미 코드 작성·수정·테스트, 하위 에이전트, 병렬 및 백그라운드 작업을 지원하는 방향으로 발전하고 있습니다. 반면 이번 설계는 개별 코딩 능력보다 **여러 개발 요청이 지속적으로 발생하는 환경에서 에이전트를 어떻게 조직하고 운영할 것인가**에 무게를 둡니다.

| 비교 관점 | 일반적인 코딩 에이전트 사용 | DeepSeek Super-agent가 강조하는 방향 |
|---|---|---|
| 주요 관심사 | 개발 작업 수행 | 개발 업무의 지속적인 조정과 실행 |
| 작업 시작 | 사용자가 작업을 요청 | 요청 및 허용된 이벤트가 작업을 유발 |
| 여러 작업 | 세션 및 하위 에이전트 활용 | Router가 독립 Worker에게 작업 할당 |
| 상태 관리 | 개발자가 세션을 확인 | 작업·이벤트·담당 Worker 연결 |
| 협업 방식 | 대화 및 개발 도구 중심 | GitHub·메신저 등 업무 채널 중심 |
| 사람의 역할 | 지시 및 결과 검토 | 목표·정책 설정과 주요 의사결정 |

이는 제품의 기능 우열 비교가 아니라 설계상 강조점의 차이입니다. OpenAI와 Anthropic도 개발 도구를 업무 환경에 통합하고 에이전트 실행을 자동화하는 기능을 계속 확장하고 있어, 이 방향이 딥시크만의 접근이라고 볼 수는 없습니다. 실제 경쟁력은 아키텍처 이름보다 개발 현장에서 얼마나 안정적으로 작동하는지에 따라 갈릴 것입니다.

<br/>

## 9. 도입 전에 반드시 따져야 할 문제

흥미로운 프로젝트지만 현재 상태에서 무작정 도입하기에는 위험 요소가 있습니다.

### 실행 권한 — 가장 주의할 부분

공식 배포 문서에 따르면 Router와 Worker의 실행 프리셋은 **운영체제 사용자 권한으로 명령을 실행하며 `danger-full-access` 권한을 사용**합니다.

문서는 더 분명하게 적고 있습니다. 계정 래퍼가 에이전트의 자격증명을 선택할 뿐 **프로세스를 격리하지는 않으며**, Worker는 경로를 지정해 프로그램을 실행하고 운영자의 홈 디렉터리를 읽을 수 있습니다. 격리가 필요하면 **에이전트 자격증명만 담긴 전용 OS 계정**을 쓰라고 권고합니다.

GitHub 계정을 따로 설정해도 실행 프로세스 자체가 OS 수준에서 격리되는 것은 아니라는 뜻입니다.

### 프롬프트 인젝션

GitHub 이슈나 댓글은 **외부 입력**입니다. 에이전트가 이를 그대로 신뢰하고 명령을 실행한다면 악의적 지시가 포함된 프롬프트 인젝션에 노출될 수 있습니다. 별도 OS 계정, 최소 권한, 격리된 실행 환경, 비밀정보 접근 제한이 필요합니다.

### 코드 변경 충돌

여러 Worker가 같은 소스를 수정하면 Git 충돌이나 논리적 오류가 생길 수 있습니다. 독립 실행 환경이 있다고 해서 통합 문제가 사라지지는 않습니다.

### 토큰 비용

여러 Worker가 동시에 모델을 호출하면 단일 에이전트보다 많은 API 요청과 토큰이 발생합니다. 공식 실험에서도 완료 시간은 개선됐지만 캐시 읽기 토큰은 3.8배 늘었습니다. 도입 시에는 완료 시간뿐 아니라 **전체 API 비용과 자원 사용량을 함께 측정**해야 합니다.

### 결과 검증

AI가 수정한 코드가 요구사항을 충족하는지, 테스트를 통과했는지, 기존 기능에 영향이 없는지 확인해야 합니다. 특히 운영 환경으로 가는 PR 병합은 사람의 검토를 거치는 것이 안전합니다. 공식 설치 가이드도 **자동 병합을 기본적으로 비활성화**하도록 안내하며, "에이전트의 PR이 한동안 문제없이 나온 뒤에 켜라"고 권합니다.

<br/>

## 10. 이번 발표에서 가장 주목할 변화

이번 발표에서 주목할 부분은 AI가 코드를 얼마나 잘 쓰느냐가 아닙니다. **AI가 수행할 작업을 어떻게 발견하고, 분배하고, 관리하며, 사람에게 필요한 순간에만 개입을 요청하도록 만들 것인가**라는 질문에 접근했다는 점입니다.

그동안 코딩 에이전트는 사람이 지시하고 AI가 결과를 만드는 형태에 가까웠습니다. 앞으로는 개발팀이 쓰는 GitHub, 이슈 관리 시스템, 메신저, CI/CD 환경과 에이전트가 직접 연결되는 방식이 더 중요해질 수 있습니다. 개발자가 모든 오류 수정을 직접 지시하지 않아도, 허용된 범위에서 에이전트가 문제를 발견하고 분석해 검토 가능한 PR을 준비하는 식입니다.

그렇다고 사람이 필요 없어지는 것은 아닙니다. 오히려 자동화할수록 **작업 권한을 어디까지 허용할지, 결과를 어떻게 검증할지, 문제가 생기면 누가 책임질지** 결정하는 일이 중요해집니다.

이런 관점에서 슈퍼 에이전트의 핵심은 사람을 개발 과정에서 빼는 것이 아니라, **사람이 반복적인 작업 관리에서 벗어나 더 중요한 판단과 검증에 집중하도록 만드는 것**이라고 볼 수 있습니다.

물론 아직 초기 단계입니다. 공개된 프로토타입을 완성된 자동화 플랫폼으로 보기는 어렵고, 실제 프로젝트에서 안정적으로 쓸 수 있는지도 추가 검증이 필요합니다. 하지만 여러 AI 에이전트가 독립적으로 작업하면서도 하나의 시스템처럼 동작하도록 만드는 설계는, 앞으로 AI 개발 도구가 나아갈 중요한 방향 중 하나로 보입니다.

코딩을 대신해 주는 AI에서, 개발 업무의 흐름에 지속적으로 참여하는 AI로. 이번 딥시크의 발표는 그 변화를 보여주는 사례입니다.
