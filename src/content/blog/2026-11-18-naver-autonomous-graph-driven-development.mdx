AI 코딩 도구를 쓰다 보면 한 가지 벽에 부딪힙니다. **AI가 일은 잘하는데, 그 일을 시키는 건 결국 사람**이라는 것입니다. 노트북을 닫으면 개발도 멈춥니다.

네이버 사내 기술 교류 행사 **NAVER Engineering Day 10th**에서 발표되고 D2에 공개된 **「노트북을 닫아도 개발은 계속된다: 자율 그래프 주도 개발」** 세션은 이 문제를 정면으로 다룹니다. 발표자는 NAVER Cloud AI Factory Tech의 **이관택** 님입니다.

핵심은 주도권의 역전입니다. **사람이 AI를 호출하던 구조를, AI가 필요할 때만 사람을 호출하는 구조로 뒤집었습니다.**

이 글은 [D2 공개 글](https://d2.naver.com/helloworld/5976687)과 24분 38초 분량의 발표 영상 슬라이드를 함께 확인해 정리했습니다.

<br/>

## 문제: 여전히 사람이 주도한다

발표는 AI 협업의 빈자리를 세 가지로 정리합니다.

- **시킨 일은 잘하지만 시키는 건 결국 사람**
- **AI는 기다리는데 사람은 인지 과부하**
- **노트북을 닫으면 개발도 중단**

여기에 "요구사항은 항상 변한다"는 현실이 겹칩니다. 기획서가 바뀌면 스펙과 코드가 연쇄적으로 흔들리는데, 그 변화를 사람이 일일이 AI에게 전달해야 한다면 자동화의 이득이 상쇄됩니다.

<br/>

## 접근: 그래프가 프로젝트를 주도한다

**자율 그래프 주도 개발(Autonomous Graph-Driven Development)** 은 사람의 직접 지시 없이 그래프가 진행을 주도하는 방식입니다. 스펙 문서와 코드는 AI 에이전트 루프가 쓰고, **결정론적 코드가 이를 기계적으로 검사**하며, 결함은 피드백 루프로 되돌아갑니다.

발표의 표현을 빌리면 **"Don't call us, we'll call you"** 입니다.

### 그래프의 핵심 원칙 3가지

![그래프의 핵심 원칙 — SSOT, 다섯 개의 노드, Open Question](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_principles.webp)

*이미지 출처: [NAVER D2 — 노트북을 닫아도 개발은 계속된다](https://d2.naver.com/helloworld/5976687) 발표 영상*

| 원칙 | 내용 |
|---|---|
| **SSOT** | 루프는 매번 새 세션으로 시작하고, 컨텍스트는 저장소 한 곳에 둔다 (요구사항·진행 상태·API 계약·인수 조건·E2E 테스트) |
| **다섯 개의 노드** | 서로 호출하지 않고 독립적이며, 몇 번을 돌려도 결과가 같다(**멱등**) |
| **Open Question** | 추측하지 않고 질문한다. 답이 올 때까지 중단한다 |

세 번째가 특히 인상적입니다. 사람은 **결정만 하고 잊으면 됩니다(Decide and forget).** AI가 애매한 지점에서 멋대로 추측하지 않고 멈춰 서서 묻기 때문에, 사람이 진행 상황을 계속 지켜볼 필요가 없습니다.

### 그래프 구조: 5개 노드와 엣지

![그래프 구조 — Upstream, Spec-drive, Dev, Verify, Audit 5개 노드](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_graph.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

노드는 **AI 루프와 결정론적 코드**로 구성되고, 엣지는 **스펙의 상태 전이**입니다.

| 노드 | 역할 |
|---|---|
| ① **Upstream** | 기획서 변경을 요구사항으로 옮긴다 |
| ② **Spec-drive** | 계약·인수 조건·E2E를 확정한다 |
| ③ **Dev** | 확정된 스펙을 구현한다 (구현 PR → 병합) |
| ④ **Verify** | 배포된 코드를 E2E로 검증한다 |
| ⑤ **Audit** | main 전체의 논리적 결함을 찾는다 |

주목할 부분은 **피드백 엣지**입니다. Verify가 실패하면 `[Bug] 티켓 → 재작업`으로 Dev에 돌아가고, Audit이 결함을 찾으면 `[Spec] 이슈 → 강등`으로 Spec-drive까지 되돌아갑니다. 사람은 그래프 위쪽에서 **질문 답변 · [Spec] 발의 · PR 승인 · [Bug] 티켓**만 담당합니다.

<br/>

## 노드 ③ Dev: PR의 84%를 루프가 썼다

![노드 Dev — 확정된 스펙을 구현한다](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_dev.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

Dev 노드의 흐름은 이렇습니다. **Catalog(확정 요구사항) → 티켓 발행 → 구현 PR → PR 리뷰 → Spec Gate → PR 승인(사람)**. 각 단계마다 담당이 `코드`인지 `AI`인지 `사람`인지가 명시되어 있습니다.

설계에서 눈에 띄는 장치 세 가지입니다.

- **100턴 한도**: 한 세션이 50분 안에 끝나 다음 사이클과 겹치지 않게 하고, 비용·품질 저하와 무한 작업을 막습니다
- **Draft PR 저장**: 턴 한도에 걸리면 진행분을 커밋해둬 다음 사이클이 이어서 작업합니다
- **10회 연속 중단 시 결정 요청**: 루프가 같은 자리를 맴돌면 사람에게 넘깁니다

결과는 **그래프 가동 후 기능 구현 PR 77건 중 84%를 루프가 작성**했습니다.

## 노드 ⑤ Audit: 합치면 어긋나는 곳을 찾는다

![노드 Audit — 스펙의 논리적 결함을 찾는다](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_audit.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

Audit은 이 방법론에서 가장 독특한 노드입니다. **PR 하나씩은 맞지만 합치면 어긋나는 곳**을 찾아 사람에게 수정 여부를 묻습니다.

검증 대상은 **의미 중복 정의 · 무효 근거 인용 · 교차 인수 조건 모순**입니다. main이 변경될 때와 야간에 돌며, 실행당 최대 5건까지 `[Spec] 이슈`를 발행하고 중복은 회피합니다.

**12주 동안 Audit 노드가 스펙 결함 17건을 찾아냈습니다.**

<br/>

## 성과 ①: 리드타임 — 대부분은 사람을 기다린 시간

![성과 리드타임 — 사람의 결정만 남는다](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_leadtime.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

| 구간 | 전체 소요(중앙값) | 그중 루프 실제 실행 |
|---|---|---|
| 기획서 변경 → 카탈로그 반영 | 1.6시간 (57건) | 약 16분 |
| 카탈로그 반영 → 스펙 확정 | 4.2시간 (92건) | 세션 평균 약 9분 |
| 스펙 확정 → 구현·E2E 검증 완료 | 6일 (18건) | 2.0시간 (하루 평균 4건 동시) |

이 표의 핵심은 **막대의 대부분이 회색**이라는 점입니다. 회색은 "질문 이슈 답변·PR 승인 대기", 즉 **사람의 결정을 기다린 시간**입니다. 루프 자체는 16분, 9분, 2시간 만에 끝냅니다.

그래서 **루프가 쓴 PR 634건 중 341건(54%)은 업무시간 밖(야간·주말)에 작성되어 사람의 승인을 기다렸습니다.** 제목의 "노트북을 닫아도 개발은 계속된다"가 수치로 확인되는 지점입니다.

## 성과 ②: 백엔드 개발 공수 86% 절감

![성과 인력 — 백엔드 개발 공수 86% 절감](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_people.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

| 구분 | 공수 | 절감 |
|---|---|---|
| 기존 방식 견적 (백엔드 2명 × 3개월) | 6 M/M | — |
| 그래프 적용 (제품 + 스펙 + **그래프 운영 도구**, 약 348h) | 2.2 M/M | 63% |
| 그래프 적용 (제품 + 스펙, 약 137h) | **0.86 M/M** | **86%** |

여기서 정직한 부분이 있습니다. **사람 공수의 60%를 그래프 운영 도구를 만드는 데 썼습니다.** 그 비용까지 포함해도 63% 절감이라는 것이고, 도구 개발을 제외한 순수 제품 개발 기준이 86%입니다.

발표는 이를 **"사람은 도구를 만들고, 루프는 제품을 만든다"** 로 정리합니다.

요구사항 1건을 검증 완료까지 끝낸 토큰 비용은 **중앙값 $69**, 그래프가 안정화된 뒤에는 **$36**이었습니다.

## 처음부터 잘 굴러가지는 않았다

발표에서 가장 값진 부분은 성과가 아니라 실패 기록입니다. **"그래프 자체가 또 하나의 제품이었다"** 는 고백으로 시작합니다.

### 어려움 ①: 루프는 눈치채지 못했다

![어려움 — 루프 안정화: 루프는 눈치채지 못했다](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_stability.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

- **작성한 코드가 사라졌다**: AI는 자기 세션이 몇 턴째인지 모르기 때문에, 턴 한도에 걸린 세션이 산출물 없이 끝났습니다. 루프는 이를 알아채지 못해 몇 사이클 동안 같은 작업을 반복했고 코드는 전량 유실됐습니다
  - **해결**: 세션 시작과 동시에 Draft PR을 열고 주기적으로 커밋, 남은 커밋은 운영 도구가 자동 푸시
- **기획서가 병합보다 빨리 바뀌었다**: 기획서 전체를 지문 하나로 대조해서, 무관한 화면 하나만 바뀌어도 **스펙 문서 36건이 한꺼번에 낡았습니다.** 카탈로그 PR이 병합되기도 전에 다음 변경이 감지돼 PR이 닫혔다 열리기를 반복했습니다
  - **해결**: 지문을 파일 단위로 쪼개 실제로 바뀐 문서만 낡은 것으로 표시, 전체 스캔은 새벽 하루 한 번으로 축소

### 어려움 ③: 애매한 문장은 AI도, 사람도 오해한다

가장 곱씹을 만한 사례입니다. 기획서의 **"세션 종료 이후의 대화는 '새 세션'으로 시작"** 이라는 문장을 두고,

- **기획자의 뜻**: 대화를 차단하고 사용자가 새 세션을 연다
- **AI의 해석**: 자동으로 새 세션으로 넘겨 이어 간다(롤오버)

AI는 자기 해석대로 구현해 **E2E 테스트까지 통과했고, 사람이 버그로 발견하고 나서야 드러났습니다.**

발표의 결론 문장이 날카롭습니다. **"규칙은 '근거가 있는가'는 검사해도 '근거를 제대로 이해했는가'는 검사하지 못한다."**

## 임팩트: 사람에게 남을 일과 사라질 일

![Human-in-the-loop — 사람에게 남을 일, 사라질 일](/images/blog/2026-11-18-naver-autonomous-graph-driven-development_hitl.webp)

*이미지 출처: [NAVER D2](https://d2.naver.com/helloworld/5976687) 발표 영상*

진행의 주도권이 AI로 넘어가면서 사람에게는 여섯 가지 일만 남았습니다.

| 구분 | 일 | 설명 |
|---|---|---|
| **남을 일** | 질문 이슈 답변 | 무엇이 맞는지는 AI에 맡기지 않는다 |
| **남을 일** | [Spec] 이슈 발의 | 기획서에 없는 기능을 직접 제안한다 |
| **남을 일** | PR 승인 | 스펙과 코드 병합의 최종 책임을 진다 |
| 사라질 일 | 트리아지 이슈 검토 | AI가 발견한 스펙 결함을 고칠지 정한다 |
| 사라질 일 | [Bug] 티켓 발행 | E2E가 못 잡은 버그를 직접 보고한다 |
| 사라질 일 | needs-decision 확인 | 잘못된 방향으로 계속 가지 않게 한다 |

발표는 **모델이 더 발전하면 권한과 책임이 필요한 세 가지만 끝까지 남을 가능성이 크다**고 전망합니다. 질문에 답하고, 없는 것을 제안하고, 최종 책임을 지는 일입니다.

### 확장 가능성: 그래프 운영 도구에는 서비스 지식이 없다

재사용 가능한 자산과 프로젝트 커스텀 영역이 분리되어 있다는 점도 중요합니다.

- **다시 쓰는 자산**: 그래프 운영 도구, 규칙 문서(ID 체계·상태 전이표·PR 규칙), AI 에이전트 스킬, **회귀 테스트 709건**
- **입력 어댑터**(프로젝트 커스텀): 기획서 페이지, Jira, Confluence, 이슈, 파일, 로그
- **출력 어댑터**(프로젝트 커스텀): 다른 저장소 통합, 배포 시스템

노드와 엣지 규칙은 어느 서비스에나 적용할 수 있고, 입출력 어댑터만 갈아 끼우면 된다는 설계입니다.

## 읽으면서 짚어둘 점

좋은 사례지만 그대로 일반화하기 전에 고려할 부분들입니다.

- **단일 프로젝트, 12주 기록입니다.** NCLOUD AI 기반 고객지원 포털 프로젝트 하나의 2026년 9월 28일 기준 수치이고, 비교 대상인 "6 M/M"은 실측이 아니라 **기존 방식 견적**입니다
- **백엔드 한정입니다.** 86%는 백엔드 개발 공수 기준이고, FE까지 포함한 제품 전체 완성은 발표가 꼽은 **다음 과제**입니다
- **초기 투자가 큽니다.** 사람 공수의 60%가 그래프 운영 도구 개발에 들어갔습니다. 이 도구를 재사용할 수 있는 조직이라야 수치가 유지됩니다
- **스펙 기반 개발 자체의 효과는 아직 독립 검증이 부족합니다.** 업계 전반에서 spec-driven development가 결함을 줄인다는 독립 연구는 2026년 11월 기준으로도 나오지 않았습니다. 이 사례는 잘 설계된 단일 조직 사례로 읽는 것이 적절합니다

<br/>

## 정리

1. **구조**: Upstream → Spec-drive → Dev → Verify → Audit 5개 노드, 서로 호출하지 않고 멱등하게 동작
2. **원칙**: SSOT(저장소 한 곳) · 독립 노드 · Open Question(추측 대신 질문, Decide and forget)
3. **코딩**: 기능 구현 PR 77건 중 **84%를 루프가 작성**, 100턴/50분 한도와 Draft PR로 유실 방지
4. **검증**: Audit 노드가 12주간 **스펙 결함 17건** 발견 (합치면 어긋나는 지점)
5. **리드타임**: 루프 실행은 16분~2시간, 나머지는 대부분 **사람의 결정을 기다린 시간**. PR 634건 중 **54%가 야간·주말에 작성**
6. **비용**: 백엔드 공수 **86% 절감**(도구 개발 포함 63%), 사람+AI 합산 **71% 절감**(구축 포함 38%)
7. **모델**: 반복 루프는 **Sonnet 5로 충분**, 최상위 모델은 구축과 사람 협업에만. 요구사항 1건당 중앙값 $69 → 안정화 후 $36

가장 기억에 남는 문장은 어려움 ③의 결론입니다. **"규칙은 '근거가 있는가'는 검사해도 '근거를 제대로 이해했는가'는 검사하지 못한다."** 자동화를 아무리 정교하게 짜도, 애매한 문장을 걸러내는 일은 여전히 사람 몫으로 남는다는 뜻입니다.

[지난 바이브 코딩 포스팅](/blog/vibe-coding-quality-tips)에서 "AI에게 자유도를 무제한으로 주지 말고 재료와 선택지를 좁혀주자"고 정리했는데, 이 사례는 그 원칙을 **조직 단위 프로세스로 확장한 형태**로 볼 수 있습니다.
