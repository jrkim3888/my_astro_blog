AI에게 "앱 만들어줘", "이런 화면 만들어줘"라고 던지면 생각보다 빠르게 결과물이 나옵니다. 그런데 막상 받아보면 기능은 돌아가는데 **어딘가 조잡하고 통일성이 없어 보이는** 경우가 많습니다. 색이 제각각이거나, 화면마다 아이콘 스타일이 다르거나, 한 부분을 고치면 다른 부분이 깨지는 식입니다.

이 "2% 아쉬움"은 사실 AI의 한계라기보다, **AI에게 일을 맡기는 방식의 문제**인 경우가 많습니다. 몇 가지 작업 습관만 바꿔도 결과물의 완성도가 눈에 띄게 달라집니다.

<br/>

## 1. 바로 구현시키지 말고, 목업부터 여러 개 뽑기

결과물이 어설퍼 보이는 가장 큰 이유 중 하나는 **첫 시도를 그대로 밀고 나가기 때문**입니다. AI에게 한 번에 완성본을 만들라고 하면, 당장 돌아가는 수준에서 멈춰버리기 쉽습니다.

![여러 UI 시안을 나란히 놓고 비교해 하나를 고르는 모습](/images/blog/2026-10-26-vibe-coding-quality-tips_1.webp)

- 바로 구현을 요청하기 전에, **여러 개의 UI 시안(목업)을 나란히 뽑아달라고** 요청합니다.
- 그중 마음에 드는 시안을 고르고, **그 목업을 기준점으로 남겨둔 채** 구현을 진행합니다.
- 이렇게 하면 "일단 되는 것"과 "원하는 모습"의 간극이 크게 줄어듭니다.

<br/>

## 2. 화면·파일을 통째로 만들지 말고, 잘게 쪼개서 요청하기

하나의 거대한 파일이나 화면을 한 번에 만들어달라고 하면, AI가 참고해야 할 맥락이 많아지고 실수할 여지도 커집니다. 반대로 **작업을 모듈 단위로 쪼개서** 요청하면 결과물의 일관성이 올라갑니다.

![헤더·사이드바·카드 등 컴포넌트를 따로 만들어 화면에 조립하는 모습](/images/blog/2026-10-26-vibe-coding-quality-tips_2.webp)

- 화면 하나를 통째로 요청하기보다, 헤더·리스트·버튼 같은 **컴포넌트 단위로 나눠서** 작업을 시킵니다.
- 모듈이 작을수록 AI가 한 번에 읽어야 할 코드량이 줄어들고, **한 부분을 수정했을 때 다른 부분이 깨지는 부작용**도 줄어듭니다.
- 결과적으로 수정·디버깅 속도도 훨씬 빨라집니다.

<br/>

## 3. 색상 팔레트를 먼저 정해두고, 그 안에서만 쓰게 하기

화면마다 색이 조금씩 다르거나, 강조색을 남발해서 전체적으로 산만해 보이는 경우가 흔합니다. 이건 AI에게 **색상의 "재료"를 미리 정해주지 않아서** 생기는 문제입니다.

![제각각이던 색을 걸러 소수의 팔레트로 정리하자 화면이 차분해지는 모습](/images/blog/2026-10-26-vibe-coding-quality-tips_3.webp)

- 직접 색상 체계를 만들기 어렵다면, Tailwind나 Open Color 같은 **공개된 색상 팔레트 중 한 계열을 그대로 가져와** 그 안에서만 쓰도록 지정합니다.
- 메인 색은 하나로 고정하고, 경고·에러 같은 강조색은 꼭 필요한 곳에만 제한적으로 씁니다.
- "이 팔레트 안에서만 색을 써라"는 한 줄 지침만으로도 화면 전체의 톤이 훨씬 차분하고 통일감 있게 정리됩니다.

<br/>

## 4. 아이콘·폰트 같은 '재료'를 통일하기

색상만큼이나 아이콘과 글자체도 전체 인상을 좌우합니다. AI가 매번 다른 스타일의 아이콘이나 폰트를 섞어 쓰면, 디테일 하나하나는 괜찮아도 전체적으로는 **짜깁기한 느낌**을 줍니다.

![아이콘 세트와 폰트, 색상 토큰을 하나로 정리해 화면에 일관되게 적용한 모습](/images/blog/2026-10-26-vibe-coding-quality-tips_4.webp)

- 아이콘은 특정 아이콘 세트(무료로 쓸 수 있는 토스페이스 같은 모음)로, 글자는 특정 폰트(프리텐다드 등) 하나로 고정해서 쓰게 합니다.
- 재료를 통일하는 것만으로도 완성도가 체감상 크게 올라가는, **비용 대비 효과가 가장 좋은 작업**입니다.

<br/>

## 5. 실기기에서 직접 돌려보고, 검증 단계를 나누기

화면상으로는 멀쩡해 보여도 실제로 설치해서 써보면 다른 문제가 보이는 경우가 많습니다. 테스트 단계도 역할을 나눠서 진행하면 더 꼼꼼하게 걸러낼 수 있습니다.

![실제 기기에서 앱을 돌려보고 AI가 따로 문제를 찾아내는 모습](/images/blog/2026-10-26-vibe-coding-quality-tips_5.webp)

- 가능하다면 **AI가 직접 기기에 연결해 앱을 실행하고 화면을 확인**하도록 합니다.
- 만든 사람이 아닌 **다른 AI(또는 다른 세션)에게 "문제만 찾아달라"고 검증을 맡기면** 놓친 부분을 더 잘 잡아냅니다.
- 다만 AI가 화면을 "눈대중"으로 클릭하다 의도치 않은 동작(예: 실수로 다른 버튼을 누르는 등)을 일으킬 수 있으므로, **화면 구조를 정확히 읽고 좌표가 아닌 요소 기준으로 동작하도록** 규칙을 정해두는 것이 안전합니다.
- 버그를 하나 고칠 때마다 **같은 문제가 재발하지 않는지 확인하는 테스트**를 같이 남겨두면, 다음 수정 때 같은 실수를 반복하지 않습니다.

<br/>

## 정리하면

결국 핵심은 하나입니다. **AI에게 자유도를 무제한으로 주지 말고, 선택지와 재료를 미리 좁혀준 다음 맡기는 것**입니다.

### 핵심 정리
1. **목업 먼저**: 바로 구현 대신 여러 시안을 비교하고 기준을 정한 뒤 진행
2. **모듈화**: 화면·파일을 잘게 쪼개서 요청해 일관성과 안정성 확보
3. **색상 팔레트 고정**: 공개 팔레트 등을 활용해 색을 정해두고 그 안에서만 사용
4. **아이콘·폰트 통일**: 재료를 하나로 고정하는 것만으로 완성도가 크게 상승
5. **실기기 테스트 + 역할 분리 검증**: 직접 실행·확인하고, 다른 AI에게 문제 발견을 맡기고, 재발 방지 테스트를 남기기

AI가 뭐든 빠르게 만들어주는 시대일수록, 결과물의 완성도를 가르는 건 **AI의 실력보다 일을 맡기는 방식**인 것 같습니다.
